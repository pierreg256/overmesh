# ADR-0014 — Use delimiter-safe ordered catalogue keys

- **Status:** accepted
- **Date:** 2026-08-23
- **Milestone:** 0.12.0
- **Supersedes:** —
- **Superseded by:** —
- **Amends:** ADR-0004, ADR-0006, ADR-0007, ADR-0008

## Context

ADR-0008 encodes each catalogue-key byte as two hexadecimal characters. The
encoding is monotone and prefix-preserving, but it has two independent costs.

First, it approximately halves the usable ASCII blob-name budget. ADR-0004
already records that compatibility defect.

Second, it removes every logical delimiter from the physical key. Azure can
collapse a listing only at a delimiter present in the stored name. Using
`delimiter=2f` for an encoded `/` is incorrect because `2f` can also straddle
two adjacent encoded bytes.

The corrected 5,000-entry listing confirmation makes the operational cost
exact. Each hierarchical repetition returns 50 prefixes, considers 5,004
catalogue keys and validates 54 candidates. Validation costs 216 reads, while
walking the opaque Azure pages costs 927 catalogue-page requests plus 15
quarantine-prefix listings. Part A removed unnecessary validation, but
enumeration remains proportional to the number of blobs.

An encoded-range cursor was considered first and withdrawn. Azure List Blobs
offers no `start-after` primitive. Its `NextMarker` is generated by the service
and opaque, so lexicographic ordering does not make the catalogue seekable.

## Options considered

**Synthesize an encoded upper-bound marker.** Rejected because Azure markers
are opaque. A synthetic value is outside the backend contract and would also
change the raw cursor map covered by signed continuation tokens.

**Maintain a secondary prefix index.** Rejected. It adds a signed document type
whose truth can drift from the committed head, conditional writes for every
new prefix, ambiguous last-descendant deletion, and a reconciliation protocol.
A reference count is not derivable from one validated `W=2` head, while
rebuilding the index requires the full catalogue scan this design is intended
to avoid.

**Use a monotone, prefix-free encoding that preserves `/`.** Chosen. It keeps
the catalogue entry equal to the signed committed head, restores near-native
ASCII name capacity, and lets Azure collapse the common hierarchical
delimiter without introducing a second index.

## Decision

Catalogue generation 2 uses:

```text
catalog/v2/{ordseq(container)}!/{ordseq(blob)}!
```

`ordseq/v1` encodes UTF-8 bytes with a prefix-free monotone code:

- trail alphabet:
  `-0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZ_abcdefghijklmnopqrstuvwxyz`;
- bytes `0x00` through `0x23`: `"` followed by trail position `byte`;
- bytes `0x24` through `0x2D`: the byte itself;
- byte `0x2E` (`.`): `.-`;
- bytes `0x2F` through `0x7A`: the byte itself;
- bytes `0x7B` through `0xBA`: `{` followed by trail position
  `byte - 0x7B`;
- bytes `0xBB` through `0xFA`: `|` followed by trail position
  `byte - 0xBB`;
- bytes `0xFB` through `0xFF`: `}` followed by trail position
  `byte - 0xFB`;
- `!` terminates a complete catalogue entry and appears in no codeword.

The trail alphabet is ASCII-ordered and contains neither `!` nor `/`.
Consequently `/` appears in an encoded component if and only if the source
contains byte `0x2F`. The terminator sorts below every codeword lead, so a name
sorts before every longer name for which it is a prefix.

Encoding `.` rather than passing it through is required for URL safety. No
encoded path segment can equal `.` or `..`, so RFC 3986 dot-segment
normalization cannot map two logical catalogue keys onto one backend object.

Every encoded component is terminated. This is required for cross-container
ordering: without the first `!`, a container such as `photo-s` would sort
before `photo/` because `-` sorts below `/`. The structural separator is
therefore always preceded by a terminator that cannot occur inside a component.

The exact mapping is part of the format. It must not be replaced by a merely
similar escaping scheme.

### Native delimiter scope

Generation 2 delegates only the one-character `/` delimiter to Azure. Other
supported delimiters retain the current client-side collapse path. This mode
selection is fixed by the signed catalogue generation in the Ring, never by a
per-replica or per-Gateway setting.

The backend page model gains distinct object and prefix entries and sends
`delimiter=/` with the encoded physical prefix. Opaque Azure markers remain
opaque and continue to be retained separately per backend. Cross-backend safe
upper bounds are computed over one ordered union of object keys and prefix
strings. A listing request encodes the logical prefix without the final blob
terminator; stored complete entries retain it.

A backend `BlobPrefix` is not sufficient evidence for a client-visible prefix.
Before emitting it, the Gateway performs a flat listing scoped to that encoded
prefix and validates a bounded initial candidate set concurrently under the
global listing limiter. If none validates, it falls back to the current flat
scan for that group until one healthy catalogue/head pair is found or the group
is exhausted.

Nominal work is therefore proportional to the number of prefixes and preserves
the existing rule that every emitted prefix is backed by validated committed
state. The worst case for a fully invalid group is the current linear path plus
the bounded probe. Tombstoned, quarantined, incomplete and tampered-only groups
remain invisible.

The reserved `.overmesh` logical namespace is filtered immediately after a
backend prefix is decoded and can never satisfy the descendant proof.

Generation 2 does not retain tombstoned catalogue entries. DELETE first
publishes and verifies the replicated tombstone head, then conditionally
removes the catalogue entry from both replicas. The Reconciler derives the same
action from a validated `W=2` tombstone head. This prevents fully deleted
groups from becoming a permanent linear fallback on every hierarchical
listing.

### Version and rollout

Ring `apiVersion` moves to `overmesh.io/v2` and declares
`catalogueEncoding = "ordseq/v1"`. The field is included explicitly in
`RingHashPayload` and covered by the v2 Ring signature domain. Its absence,
an unknown value, a v1 document, or a hash that omits it is rejected rather
than defaulted. Gateway and Reconciler therefore cannot derive different key
spaces from one valid Ring.

Continuation tokens move to `overmesh.io/continuation-token/v3` and tag their
state as flat or delimited so backend markers from the two modes are never
interchanged. A v2 token fails with `400 InvalidMarker` after the Ring change
rather than resuming in a different key space.

V1 uses a greenfield transition: no dual-read, dual-publish or backfill path is
introduced. Any deployment containing generation-1 catalogue entries must be
recreated. A later non-greenfield transition requires a separate migration
decision.

### Storage-account and name constraints

The encoding introduces real path separators. Generation 2 therefore requires
flat-namespace Storage Accounts and validates the Azure path-segment limit
before accepting a logical name. Empty logical segments and a trailing `/`
remain supported exactly as they are today; startup refusal of
hierarchical-namespace accounts makes that guarantee independent of backend
variation.

System-container object URLs must encode the complete blob path before this
format is enabled, and the URL path must round-trip without dot-segment
normalization. Raw interpolation is safe for hexadecimal keys but would
misinterpret ordseq bytes such as `%` and `?` as URL syntax.

The exact generation-2 length bound is:

```text
14 + |container| + |ordseq(blob)| <= 1024
```

Container characters all use one code unit. With a ten-byte container, a blob
therefore has a 1,000-unit encoded budget: 1,000 ASCII characters in the best
case, 500 ASCII characters in the guaranteed worst case, 250 two-byte
characters, 166 three-byte characters, or 125 four-byte characters. With a
63-byte container, the corresponding limits are 947, 473, 236, 157 and 118.
The compatibility matrix publishes both ASCII bounds rather than treating a
typical mix as a limit.

A flat-namespace backend permits 254 path segments in a blob name. The fixed
`catalog/v2/{container}!` prefix consumes three, so a logical blob may contain
at most 251 segments, counting empty and trailing segments. This is a
generation-2 compatibility deviation from direct Azure Blob Storage.

The derived length and segment bounds remain part of
`LogicalBlobId::parse` through `catalog_key_length`. Before implementation,
`COMPATIBILITY.md` gains the exact generation-2 budgets and the physical
segment deviation.

## Consequences

Healthy hierarchical listing becomes proportional to returned prefixes rather
than all descendant blobs while keeping four validation reads per selected
candidate.

Listing telemetry distinguishes candidates considered during prefix proof from
backend enumeration requests per returned prefix. The four-read
`requestsPerEntryValidated` invariant remains unchanged.

Flat listing and reconciliation keep one authoritative catalogue entry per
committed logical blob. Tombstoned heads drive replicated catalogue deletion.
No prefix counter, prefix tombstone or prefix repair state is introduced.

The format is more complex than hexadecimal. An ordering defect would silently
corrupt pagination, so implementation is blocked on exhaustive property tests
over random byte strings and boundary cases.

The physical key namespace, backend page type, signed Ring schema and
continuation-token version all change together. This is a 0.12.0 protocol
change, not a 0.11.0 hardening patch.

## Implementation status

Not implemented. ADR-0008's encoding property tests and the new delimiter
isolation, cross-container ordering, dot-segment-safe URL round-trip and
segment-bound properties are prerequisites.

## When to revisit

If Azure adds a supported `start-after` key, compare it against native
delimiter listing without assuming its continuation semantics match
`NextMarker`.

If hierarchical-namespace Storage Accounts become a requirement, redesign the
encoding and empty-segment rules together rather than weakening startup
validation.

If non-`/` delimiter workloads become material, define a format generation
whose escape alphabet isolates those delimiters before extending the native
path.
