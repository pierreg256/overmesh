# ADR-0004 — Immutable content naming in the customer container

- **Status:** accepted
- **Date:** 2026-08-17
- **Milestone:** 0.5.0 → 0.8.0
- **Supersedes:** —
- **Superseded by:** —

> **Provenance.** Rationale reconstructed from the implementation. The original
> intent was not recorded at the time, and the scheme changed three times across
> three milestones without an accompanying note. What follows is the reasoning
> the code supports, not a transcript of a decision. Treat the *properties* as
> binding and the *narrative* as best reconstruction.

## Context

ADR-0003 places customer content in the customer container, written by the
caller under the caller's own credentials, so that Azure RBAC remains the sole
authorization authority for customer data.

That creates a naming problem. The stored objects are immutable content
generations owned by Overmesh, but they live inside a namespace the customer
also writes to, lists, and holds permissions on. The scheme has to coexist with
arbitrary client blob names without colliding with them, without breaking Azure
limits, and without being manipulable by the caller.

The scheme went through three forms:

| Milestone | Content object key |
| --- | --- |
| 0.5.0 | `{blob}/.overmesh/versions/{sha256(write_id)}/{content_sha256}` |
| 0.6.0 | `.overmesh/objects/{path_hash}/{sha256(write_id)}/{content_sha256}` |
| 0.8.0 | `.overmesh/objects/{path_hash}/{uuid}` |

## Properties a scheme must satisfy

**Verifiable from the logical blob alone.** A reader holding only the signed
head must be able to check that the referenced content belongs to the blob it
claims to belong to, without trusting the manifest's own claim.

**Bounded length.** Azure caps blob names at 1,024 characters, and
`LogicalBlobId::parse` accepts client names up to that limit. Any scheme that
appends to the client's name must therefore still fit — or it turns a legal API
request into an unstorable object.

**No collision with legal client names.** `a.jpg/.overmesh/versions/x/y` is a
perfectly legal Azure blob name. A client can create it.

**Not predictable by the caller.** Content objects are written with
`If-None-Match: *` and verified on conflict. If a caller can compute the target
key in advance, they can pre-create it with different bytes; the write then
fails closed on the mismatch and the blob becomes permanently unwritable.

**Contiguous reserved region.** Overmesh's objects should collapse into a
single prefix in a direct Azure listing rather than interleave with the
customer's blobs.

## Decision

Content generations are stored at:

```
.overmesh/objects/{sha256(canonical logical path)}/{random uuid}
```

Each component earns its place:

`.overmesh/` as a **top-level** prefix rather than a suffix of the blob name.
This is what makes the key length constant — roughly 115 characters regardless
of the client's blob name — and what makes the reserved region contiguous and
filterable. The suffix form of 0.5.0 added about 140 characters to the client's
own name, so any client blob name beyond roughly 880 characters produced an
illegal storage key: a valid request that could not be stored.

`{path_hash}` binds the object to one logical blob and is derivable by any
reader from the canonical path, so the read path can verify the binding rather
than trust it.

`{random uuid}` is generated by the gateway. Every earlier form was fully
derivable from client-supplied inputs — the write ID is chosen by the caller and
the digest is the hash of their own content — which made the target key
predictable and therefore squattable. A server-generated component removes the
predictability. It also means the read path validates only the *prefix*, and
treats the final component as opaque.

## Consequences

### What it buys

Constant-length keys, so no legal client blob name is unstorable.

Squatting is no longer feasible: a caller cannot compute where the next content
generation will land.

A single reserved prefix, filtered out of Overmesh listings and trivially
recognisable in a direct Azure listing.

Uniform validation: both the read path and the reconciler's garbage collector
check one derived prefix, and reject any manifest referencing content outside
the logical blob's namespace.

### What it costs — usable blob-name length

Moving the content key out of the blob's namespace removed one length problem
and the catalogue introduced a tighter one. Both are worth stating precisely,
because together they are a **compatibility regression against calling Blob
Storage directly**.

The 0.5.0 content key appended roughly 140 characters to the client's own name,
so any client blob name beyond about 880 characters produced an unstorable
object. The current content key is constant at about 115 characters and no
longer consumes the client's budget at all.

The catalogue, introduced in 0.8.0, is now the binding constraint. Its key is:

```
catalog/v1/{hex(container)}/{hex(blob)}.json
```

`ordered_component` is `hex::encode(value.as_bytes())` — **two characters per
byte** — chosen so that lexicographic ordering of catalogue keys matches
logical ordering regardless of the bytes in the name. The budget is therefore:

```
11 + 2·|container| + 1 + 2·|blob| + 5  ≤  1024
```

with `|blob|` measured in **UTF-8 bytes**, not characters. Against Azure's own
limit of 1,024 characters, the usable name length becomes:

| Blob name content | Bytes per char | Overmesh limit | Share of Azure's 1,024 |
| --- | --- | --- | --- |
| ASCII | 1 | ~493 chars | 48% |
| Latin with accents | 2 | ~246 chars | 24% |
| CJK, Cyrillic, Greek | 3 | ~164 chars | 16% |
| Emoji, rare planes | 4 | ~123 chars | 12% |

(assuming a ten-byte container name; a maximum-length 63-byte container name
costs a further 53 characters of budget)

**This is currently a defect, not only a limitation.** `LogicalBlobId::parse`
validates the blob name at 1,024 *characters* and nothing validates the derived
catalogue key at all, so the overrun is not caught up front. Worse, the
catalogue is published *after* the committed head and the high-water record: a
write with an over-long name streams content to both replicas, publishes the
head, publishes the high-water record, and only then fails on the catalogue
write. The object is left readable by `GET` and `HEAD` but permanently absent
from listings, and the caller sees a `503`.

Two corrections are needed and neither is architectural: reject the name at
`LogicalBlobId::parse` against the real derived limit, and publish the
catalogue entry inside the same conditional sequence as the head rather than
after it. Whether the encoding itself should change — hex costs 2× where a
sortable escaping scheme could cost close to 1× for ASCII — is a separate
question worth asking before 1.0.

### What it costs — path-based ABAC becomes unsupportable

Attribute-based access control on Blob Storage is generally available, and
conditions on `…/containers/blobs:path` are one of its common uses. Under this
naming scheme they cannot be honoured.

Content is written to `.overmesh/objects/{path_hash}/{uuid}`, where
`path_hash` is a SHA-256. The logical blob name appears in no form a path
predicate can match. A condition restricting a caller to `finance/*` therefore
has no bearing on where their writes actually land.

**This is the naming decision that makes path-predicate conditions
unsupportable, and ADR-0005 is where that consequence is decided.** In short:
such conditions are honoured on read, `HEAD` and delete — which probe the
logical path — and not on write or listing, and a partially enforced
access-control condition is worse than an unsupported one. They are therefore
declared unsupported and are to be refused by the RBAC posture audit.

An earlier draft of this record recommended that administrators authorize
`.overmesh/objects*` so that deployments using such conditions would function.
That recommendation is withdrawn: following it would grant a caller write
access to the content of *every* logical blob, which is precisely the bypass
ADR-0005 identifies.

The 0.5.0 scheme did not have this problem. Content stored at
`{blob}/.overmesh/versions/…` was covered by any prefix condition on the blob
name. The move to a top-level prefix traded path-granular authorization for
constant key length and a contiguous reserved region — a trade that was not
recognised as such at the time.

`@Environment` conditions — a given private endpoint or subnet, for instance —
and `@Principal` conditions compose normally, since they do not depend on the
path. Container-scope assignments are unaffected, and because logical
containers map one-to-one onto backend containers, separation by container
works with full fidelity.

### Residual gap

The reserved prefix is filtered at *listing* time but is not refused at *write*
time. A caller can still create a logical blob named `.overmesh/anything`: it is
accepted, catalogued, and then invisible in Overmesh listings — a hidden blob.
Rejecting the prefix in `LogicalBlobId::parse` would make the reserved region
genuinely reserved, and is a small change.

## When to revisit

**A third scheme may take both.** `{blob}/.overmesh/{uuid}` sits under the blob
name, so ABAC prefix conditions cover it again; its suffix is about 45
characters rather than 140, so it is far less costly than the 0.5.0 form; and
the identifier is still server-generated, so it is not squattable.

| Scheme | ABAC prefix conditions | Content key length | Reserved region |
| --- | --- | --- | --- |
| `{blob}/.overmesh/versions/{h}/{d}` (0.5.0) | compatible | blob + ~140 | interleaved |
| `.overmesh/objects/{hash}/{uuid}` (current) | **incompatible** | constant ~115 | contiguous |
| `{blob}/.overmesh/{uuid}` (candidate) | compatible | blob + ~45 | interleaved |

The candidate loses only the contiguity of the reserved region: internal
objects would once again interleave with the customer's blobs in a *direct*
Azure listing. Overmesh's own listing already filters by prefix and would need
a different rule, and the reconciler's namespace guard would change shape.

Note that the candidate does not reintroduce the length problem in any
meaningful way, because the binding constraint is the catalogue key, not the
content key — see above. Fixing the catalogue encoding is a prerequisite for
evaluating this properly, and should come first.

**If path-predicate conditions become a deployment requirement**, this decision
is what blocks them. It must be reopened together with ADR-0005, which decides
their support status, and not in isolation — and even then, listing would
remain outside path granularity until per-entry authorization exists.

**If Azure introduces a reserved namespace within a container** that clients
cannot write to, the whole class of problem disappears and the scheme can be
simplified.

## Verified by

- `validate_committed_head` — the committed head's `content_object` must begin
  with `.overmesh/objects/{path_hash}/` (`gateway/src/read.rs`)
- The reconciler's collection planner rejects any historical manifest whose
  content or metadata falls outside the logical blob's namespace before
  deleting anything (`reconciler/src/engine.rs`)
- `listing.rs` excludes `.overmesh` and everything beneath it from listing
  results
- `harness/scripts/gateway-smoke.sh` — reads the content object back from both
  replicas at the container and key advertised by the signed manifest
